## 一、阶段结论

S 战场已经从只读预览推进到独立页面、基础交互布阵、统一内存缓存和原生 TreeView 写回事务。最近一项“补了标签仍然拒绝写入”的阻断已定位并修复：原因不是缺少标签，而是固定容量出场指令的空槽判定错误地检查了整行旧字段；真实空槽由 Data 号字段的 `-1` 标记，其他字段可能保留非零旧值。修复后，已在隔离的 S 剧本副本中完成“布阵—原生事务写入—编辑器正常保存—关闭并重新打开—重新解析确认”的窗口往返。

因此，当前状态应准确表述为：**S 预览和缓存布阵已具备可测试基底；写回入口已在普通 Debug/Release 构建开放，不再依赖 QA 标记；全部指令类别和条件分支尚未完成真实窗口覆盖。** 已有窗口往返样例不代表 0x4B/0x46/0x47 的所有新增、调整、删除、撤回及嵌套条件分支均已实测。

## 二、已完成的工作

### 1. 把 S 战场与 R 场景分成独立预览页面

- 依据剧本前缀将 R、S 剧本路由到对应页面；S 页使用自己的战场状态、坐标、字段解析和编辑操作，不读取 R 角色表，也不沿用 R 场景的角色状态与撤回逻辑。
- 两页仍可复用编辑器通用窗口宿主和基础资源，但战场数据通路与 R 场景操作分开。这解决了此前 S 页出现 R 指令诊断信息、S 逻辑被挂在 R 预览路径下的问题。
- 有 R/S 路由和隔离自动化合同；它们能证明代码边界，不能代替用户对全部窗口布局的视觉验收。

### 2. S 战场地图、视口和单位预览

- S 地图底图从 Mod 的 `map` 文件夹读取 JPG；地形/逻辑格由 `Hexzmap.e5` 解码。JPG 与地形网格尺寸不吻合或证据不完整时采取安全拒绝，不以“全地形可走”兜底。
- 地图一次展示当前战场作用域内全部已解析单位，不再按单位分页；角色列表自己的分页与地图显示相互独立。
- 地图加载默认 1:1，保留单独缩放；普通滚轮不承担地图滚动，视口使用系统滚动条和中键拖动平移。
- 地图单位不再叠加角色名称，减少单位密集处的信息遮挡。
- S 战斗形象有独立资源解析/绘制路径，并用于地图单位及待放置半透明预览；不回退到 R 角色表。

### 3. 角色列表、小兵笔刷与缓存布阵

- 角色目录从 S Mod 的 `Data.e5` 读取；角色名、Data 号和兵种信息进入独立 S 目录。小兵笔刷按相邻 Data 号及去除 ASCII 数字后的相同名称分组。
- 侧栏有“角色列表”“小兵笔刷”和显隐控制；隐藏/恢复不应重置地图视口及列表状态。地图上不显示角色名。
- 选择角色后显示正确 S 形象的半透明落点预览。小兵笔刷按住左键可在经过的新合法格连续盖章；非法地形、越界、占格等失败不消耗下一个 Data 号。笔刷支持方向滚轮；地图缩放和平移输入彼此分离。
- 右键单位提供“调整位置 / 删除”操作；既有单位依稳定 `cache_id` 定位，不以坐标或 Data 号猜对象。调整、删除、放置都先作用于统一缓存，并有 S 自己的撤回路径。
- 我军、友军、敌军通过统一的布置类别选择，不要求目标 Section 已经存在对应命令；方向、隐藏、等级、方针等暂未开放的属性保留可扩展结构并采用明确默认值。
- 小兵编号遵循已确认的批次规则：一次选用笔刷形成独立批次；删除只压紧该批，保持该批首个实际 Data 号稳定，不重排从剧本导入的既有单位。
- 缓存身份、EEX 来源锚点、最终部署类别分别建模。这个区分是支持“从无对应出场指令开始布阵”的基础，避免把来源节点误当作新增单位的前置条件。

### 4. 原生写回结构和安全边界

根据 cczEditor 源码、普罗工具 IL 和 S 样本，已经固化以下结构事实：

| 指令 | 用途 | 结构要点 |
| --- | --- | --- |
| `0x4B` | 我军出场 | 单位逐条记录；字段 0 是部署序号，不是角色 Data 号；EEX 无法持久化该记录所对应的角色身份。 |
| `0x46` | 友军出场 | 固定 20 行记录页，每行 11 个字段。 |
| `0x47` | 敌军出场 | 固定 80 行记录页，每行 12 个字段，含援军标志。 |

写回实现采用“统一缓存 → Section 级值变更计划 → 原生 TreeView 事务”的路径：先检查整个来源基线、字段完整性、目标类别、插入位置及序号，再成批更新/插入；事务同时管理节点、选择状态和文档 dirty 状态，并预备原子回滚。不得把剧本直接写成磁盘 EEX，也不复用 R 页撤回栈。

2026-09-29 起，普通 Debug/Release 构建均提供“写回”按钮，所有有效 S 战场 Section 都可通过现有原生 TreeView 事务写回。写回继续校验活动文档身份、Section/条件分支可达性、内容和树版本、来源字段、插入锚点及序号；写回修改编辑器内存，磁盘持久化仍走编辑器正常保存流程。撤回、原子回滚和写后重建预览基线继续使用同一事务实现。

### 5. S 战场快速模式与 Scene1 修改基线

- 快速模式默认开启。打开 S 剧本时不依赖当前树选择，自动在第一个 Scene（Scene1）的直接 Section 子项中定位唯一且包含有效战场地图的 Section；没有唯一候选时显示诊断，不改选其他 Scene 或 Section。
- 该 Section 是 S 预览和写回的固定来源。浏览其他 Section，或编辑剧本中其他 Section，不会把预览切走或清除当前布置缓存、未写回状态；写回仍绑定 Scene1 来源。原生撤回仍校验整份文档版本，若事务写入后又修改了任意指令，撤回会因版本过期而停止，避免覆盖后续修改。
- 玩家修改 Scene1 战场指令后，快速模式重新读取该 Section 并按新指令刷新预览、更新来源基线。指令修改不会因“版本变化”本身被拒绝。若预览中另有尚未写回的临时布置，刷新前会询问是否丢弃这些临时布置；确认后加载新指令，取消则保留旧预览与缓存并显示提示，之后仍可再次刷新。
- 写回预检按固定 Scene1 Section 的内容版本校验，因此其他 Section 的内容修改不会单独阻断 Scene1 写回；原生撤回仍校验整份文档版本，避免在文档后续变更上应用旧撤回操作。切换剧本、关闭来源窗口或退出快速模式前，对未写回的预览布置使用默认“否”的确认提示。
- 该功能已通过 CoreTests、快速模式源代码合同、S 写回与会话保留等自动化回归，并完成隔离 Debug Win32 MFC 构建。2026-09-28 已在真实窗口打开 Scene1 战场并完成一次写回、保存、关闭和重开；快速模式跨 Section 保留、Scene1 指令刷新等完整交互仍需专项验收。

### 6. S 战场条件树与可达部署

- S 页复用 R 场景的 typed `SectionExecutionModel`、条件求值规则和 `CConditionTreePane`，但独立持有条件选择状态、模型和分支工作区；不会读取或重置 R 页预览会话。
- 条件树只控制当前固定 Scene1 战场 Section 中可达的 `0x4B/0x46/0x47` 布置指令。地图与初始化数据仍按 Section 解析；无条件容器保留普通单分支行为，不冒充条件节点。
- 每个有效可达范围保存自己的预览状态和撤回栈。切换 true/else/Choice 分支后，可返回先前分支继续编辑；不可判定或映射不唯一时保留缓存，并在写回预检阶段拒绝不安全操作。
- Scene1 是来源修改基线。玩家修改 Scene1 布置指令后，预览从更新后的 Scene1 内容重新构建；这些内容变化不会仅因版本变化就被拒绝。预览中的分支切换用于查看并编辑相应可达指令，不会改绑到其他 Section。
- 新增单位的写回目标为当前分支的子事件及其直接终止 `0x00`；原生 TreeView 插入现在允许经过验证的嵌套条件/else 事件父节点。既有单位仍按来源节点身份更新/删除。
- 该设计现在接入普通“写回”入口；新增与既有原生节点的变更均通过原生事务。真实条件树窗口下的多分支写回覆盖仍待补测。

- **验收边界：**CoreTests、S 条件树合同、写回合同、快速模式/会话/笔刷/刷新路由回归和 Debug/Release Win32 构建均通过。2026-09-28 的 `0x46` 新增及一条既有 `0x47` 坐标修改已在隔离副本中保存并重开；S_12 真实条件切换、多分支布阵、三类指令完整覆盖及各类撤回仍未验收，不把自动化测试替代为窗口证据。

## 三、最近阻断问题及修复

用户补充“缺少的标签”后仍被拒绝，表面上像 Section 结构/标签证据不全。代码和失败用例进一步确认，真正的问题是 0x46/0x47 固定容量页的空槽行：空槽由 Data 号 `-1` 表示，但其他字段可能不是零。旧逻辑把这些残留字段误判为占用/不安全，导致计划器不能将新单位放入该槽。

本轮修复：

1. 空槽判定以完整字段结构已解码、Data 号为 `-1` 且该行未被编辑为准，不再要求整行其他载荷字段为零。
2. 固定页来源验证允许 `-1` 哨兵，只拒绝小于 `-1` 的 Data 号；计划应用时以规范化的新整行替换空槽，避免残留字段进入新单位。
3. 增加回归测试，确保“空槽其他字段带旧值”的真实形态仍可计划和写回。
4. 将放置状态改为说明“仍在缓存、尚未写入剧本”，QA 成功时显示成功状态，避免再把旧 Task 5 门禁文字当作实际阻断原因。

**窗口验证结果：**在隔离 QA 副本的首个 0x46 样例中，放置单位后执行 Debug QA 原生事务成功；编辑器提示事务已写入内存；随后正常保存、关闭并重新打开同一副本，重新选择对应 Section 后，新增单位仍能被解析并显示。该结果关闭了此前“连自己的测试副本都写不回”的基本阻断。
